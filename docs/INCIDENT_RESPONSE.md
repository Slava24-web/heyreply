# Реагирование на инциденты с персональными данными

Инцидент: утечка, потеря, несанкционированный доступ к данным пользователей (компрометация сервера, бакета с бэкапами, ключей, токенов, ошибка в коде, показавшая чужие данные).

## Сроки по закону

| Кому | Срок | Основание |
|---|---|---|
| Роскомнадзор: первичное уведомление, если утечка затронула права субъектов | 24 часа с момента выявления | ч. 3.1 ст. 21 152-ФЗ |
| Роскомнадзор: результаты внутреннего расследования и сведения о виновных | 72 часа | там же |
| Надзорный орган ЕС (если затронуты жители ЕС) | 72 часа, если есть риск для прав людей | ст. 33 GDPR |
| Пользователи | без неоправданной задержки, если риск высокий | ст. 34 GDPR |

Отсчёт идёт с момента, когда вы узнали об инциденте, а не с момента, когда он начался.

## Порядок действий

1. **Зафиксируйте.** Время выявления, кто и как обнаружил, что известно. Ведите журнал инцидента (по одной записи на действие).
2. **Остановите.** Что подходит по ситуации:
   - Скомпрометированы сессии или JWT-секрет: смените `JWT_ACCESS_SECRET` и перезапустите API (все access-токены станут недействительными), отзовите все сессии: `UPDATE "Session" SET "revokedAt" = now() WHERE "revokedAt" IS NULL;`.
   - Скомпрометирован токен интеграции: пользователь отзывает его в настройках; при массовой компрометации: `UPDATE "ApiToken" SET "revokedAt" = now() WHERE "revokedAt" IS NULL;`.
   - Скомпрометирован сервер: изолируйте его (закройте входящие порты, отключите от сети), сохраните диск для разбора, поднимите чистый сервер из образов и бэкапа (`docs/DEPLOY.md`), смените все секреты: `POSTGRES_PASSWORD`, `JWT_ACCESS_SECRET`, `INBOUND_SECRET`, ключи `BACKUP_S3_*`, SSH-ключи.
   - Скомпрометирован бакет бэкапов: бэкапы зашифрованы age, приватный ключ вне сервера, поэтому чтение дампа без ключа невозможно. Смените ключи доступа к бакету. Если утёк **приватный ключ age**: создайте новую пару, замените `BACKUP_AGE_RECIPIENT`, считайте все прежние копии раскрытыми.
   - Ошибка в коде показала данные другому пользователю: выкатите откат (`deploy/deploy.sh <предыдущий тег>`), определите по логам доступа, кого затронуло.
3. **Оцените.** Какие категории данных (e-mail, имя, отклики, IP, хэши паролей), сколько пользователей, чьи это пользователи (РФ, ЕС), есть ли риск для их прав (например, утечка e-mail и откликов: да). Хэши паролей argon2id и токенов SHA-256 не раскрывают секреты, но если утекли, считайте пароли подлежащими смене.
4. **Уведомите регулятора** в сроки выше. В РФ через портал РКН (форма уведомления об инциденте); для ЕС через надзорный орган страны пользователей или основного учреждения. Укажите: что произошло, категории и число субъектов, возможные последствия, принятые меры, контакт ответственного.
5. **Уведомите пользователей**, если риск высокий: письмо или сообщение в сервисе. Текст: что произошло, какие данные затронуты, что вы сделали, что делать пользователю (сменить пароль, проверить подозрительные письма от имени работодателей), контакт.
6. **Устраните причину и проверьте.** Исправление, тест, повторный аудит затронутой области; запишите в `docs/SECURITY_AUDIT.md`.
7. **Разбор.** В течение недели: хронология, причина, что изменить, чтобы не повторилось.

## Контакты
Заполните и держите актуальными: ответственный за обработку ПД, юрист, хостинг-провайдер (круглосуточный контакт), Cloudflare.
